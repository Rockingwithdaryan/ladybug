# LadyBug

A LeetCode-style app where, instead of solving problems, you **fix buggy code**. Practice problems come in Python, JavaScript, TypeScript, Java, C and C++; personal daily and weekly challenges are generated by Gemini. Your fix is graded against hidden test cases in a sandbox.

## How it fits together

One Next.js app, deployable to Vercel as is:

| Part | Path | Notes |
| --- | --- | --- |
| Pages | `app/`, `components/`, `hooks/`, `lib/` | Next.js + Monaco |
| API | `app/api/` → `server/` | Route handlers; the logic lives in `server/` |
| Database | `migrations/` | Postgres + TimescaleDB (Tiger Cloud) |
| Code runner | `runner/`, `server/sandbox.ts` | Runs user code in [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox) microVMs |

## Running locally

Requirements: Node.js 22+, [pnpm](https://pnpm.io/installation), a Postgres database with TimescaleDB (a free [Tiger Cloud](https://console.cloud.timescale.com) service works, see below), a [Gemini API key](https://aistudio.google.com/apikey), and a Vercel account for the code sandbox (the free Hobby plan is enough).

```bash
pnpm install
cp .env.example .env          # fill in DATABASE_URL, SESSION_SECRET and GEMINI_API_KEY

npx vercel link               # connect the folder to a Vercel project
npx vercel env pull           # writes .env.local with a token for Vercel Sandbox
pnpm runner:setup             # builds the sandbox snapshot; put the printed RUNNER_SNAPSHOT_ID in .env

pnpm dev
```

Open <http://localhost:3000>. Check the API with `curl localhost:3000/api/health`.

`pnpm dev` applies the database migrations in [migrations/](migrations/) first, including the seeded problem set. The token from `vercel env pull` expires after 12 hours; run it again if running code fails with an authentication error.

### Environment variables

| Variable | Required | Description |
| --- | --- | --- |
| `DATABASE_URL` | yes | Postgres with TimescaleDB, e.g. Tiger Cloud (see below) |
| `SESSION_SECRET` | yes | At least 32 characters (`openssl rand -hex 32`) |
| `GEMINI_API_KEY` | yes | Problem generation for challenges, and hints |
| `RUNNER_SNAPSHOT_ID` | yes | The code runner's sandbox snapshot, from `pnpm runner:setup` |
| `GEMINI_MODEL` | | Defaults to `gemini-2.5-flash` |
| `PUBLIC_URL` | | The app's public address, used for OAuth redirects. Defaults to `http://localhost:3000`, or the production domain on Vercel |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | | Enables "Log in with GitHub" |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | | Enables "Log in with Google" |
| `VERCEL_TOKEN` / `VERCEL_TEAM_ID` / `VERCEL_PROJECT_ID` | | Sandbox credentials for running outside Vercel without `vercel env pull` |

### OAuth

Register an OAuth app with each provider and set its callback URL to `<PUBLIC_URL>/api/auth/oauth/<provider>/callback`, for example `http://localhost:3000/api/auth/oauth/github/callback`. Login buttons only appear for providers whose credentials are set.

### Tiger Cloud

Put the service's connection string in `DATABASE_URL`, adding `uselibpqcompat=true&` before `sslmode`:

```env
DATABASE_URL=postgres://tsdbadmin:<password>@<host>:<port>/tsdb?uselibpqcompat=true&sslmode=require
```

Details in [docs/integrations.md](docs/integrations.md).

## Deploying to Vercel

1. Import the repository in Vercel. It detects Next.js; leave the root directory as the repository root.
2. Add the environment variables above under **Settings → Environment Variables**: at least `DATABASE_URL`, `SESSION_SECRET`, `GEMINI_API_KEY` and `RUNNER_SNAPSHOT_ID`. The snapshot belongs to the Vercel team you created it with, so run `pnpm runner:setup` against the same project (`vercel link`).
3. Deploy. The build command in [vercel.json](vercel.json) applies new migrations, then builds the app.
4. For a custom domain (such as the `.tech` one), add it under **Settings → Domains**, set `PUBLIC_URL` to it, and update the OAuth callback URLs.

On Vercel, the code sandbox authenticates on its own (OIDC), and HTTPS and the `X-Forwarded-For` header the rate limits use are handled by the platform. Running and debugging code can take up to a minute and generating a challenge up to five; these limits are set per route with `maxDuration` and need Fluid compute, which new projects have by default.

## Sandbox

User code never runs in the app's own functions. Each run, submit or debug session boots a fresh [Vercel Sandbox](https://vercel.com/docs/vercel-sandbox) (a Firecracker microVM) from a snapshot with every compiler and debugger preinstalled, and stops it afterwards. Each sandbox has:

- no network access at all (`networkPolicy: "deny-all"`),
- no secrets: only the job's code and test data are copied in,
- nothing shared with other jobs, since every job gets its own VM,
- a runner owned by root, plus per-run rlimits, a timeout and an empty environment within the VM.

The snapshot is built by [scripts/setup-runner.mts](scripts/setup-runner.mts), which also checks every language, with the network turned off, before printing its id. **Re-run `pnpm runner:setup` after changing anything in `runner/`** and update `RUNNER_SNAPSHOT_ID`.

Every run counts as one sandbox creation (generating a challenge uses two per attempt). The Hobby plan includes 5,000 creations a month and runs up to 10 sandboxes at once; past the monthly allowance, Hobby pauses sandbox creation until the next cycle, while Pro bills by usage.

## Development notes

- Migrations: add a new file with the next free number and never edit an applied one (they're tracked in `schema_migrations`). A file whose first line is `-- migrate:no-transaction` runs outside a transaction, which TimescaleDB continuous aggregates need. Apply them with `pnpm db:migrate` (also run by `pnpm dev` and on every Vercel deploy).
- Serverless instances share no memory, so state such as rate limit counters and in-progress challenge generations lives in Postgres ([migrations/016_serverless_state.sql](migrations/016_serverless_state.sql)).
- Generated challenge problems are only saved if the reference fix passes every test **and** the buggy code fails at least one; otherwise generation retries.
- Checks: `pnpm test`, `pnpm typecheck` and `pnpm lint`. The runner's own tests (`runner/test_regressions.py`) need Linux and run inside the sandbox as part of `pnpm runner:setup`.
